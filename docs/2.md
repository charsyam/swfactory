### Sub-issue #4: Approved issue automation

GitHub issue: [#4](https://github.com/charsyam/swfactory/issues/4) · Parent: [#3](https://github.com/charsyam/swfactory/issues/3) · Implementation PR: [#2](https://github.com/charsyam/swfactory/pull/2)

### What and why

`swfactory.py` controls a separate target GitHub repository. It polls that repository's issues bearing `accept`, breaks each issue into small tasks, implements them with the locally installed `codex exec`, tests the result, and opens a PR in the target repository. The owner retains the merge decision. This provides a reviewable boundary between automatic code changes and the main branch.

The user clones the target once and configures both its GitHub SSH URL and local checkout path. Reusing the checkout avoids downloading the full repository for every run. The checkout's `origin` is checked against the GitHub URL to avoid applying an issue to the wrong repository. A separate `WORK_DIR` contains temporary worktrees and run files; it defaults to `/tmp`.

### Sequence and design

1. Read `GITHUB_REPOGITORY`, `GITHUB_SSH_KEY_PATH`, `PROJECT_PATH`, and optional `WORK_DIR` from `env`, or override the target with `--repository` and `--project-path`. Use `/tmp` if `WORK_DIR` is absent. Verify that the existing local Git root and its `origin` match the selected GitHub repository and that `WORK_DIR` is outside the checkout. Use the SSH key only for Git fetch and push. Use the signed-in `gh` CLI for GitHub issue, label, and PR operations.
2. Optionally run `--scan` to inspect the local target checkout and create concrete bug/refactor issues without `accept`. Skip issue titles already present. A maintainer must approve a proposal by applying `accept`.
3. Acquire a local file lock so one process handles the queue at a time. Create required labels if absent. Query open `accept` issues, sort by issue number, and exclude `done`, `swfactory:running`, and `swfactory:failed`.
4. Recheck the selected issue's labels, mark it running, fetch the target's default branch, and create a temporary Git worktree under `WORK_DIR` from the local target repository's fetched commit. The target's main checkout and the `swfactory` source checkout are not modified.
5. Run Codex in read-only mode with a JSON schema. Require a summary, reason, small ordered tasks, detailed algorithms and implementation policies, task tests, and integration tests. Post the plan as a comment on the source issue.
6. Run one Codex invocation per task, in order. Each invocation sees the current worktree and the whole plan but implements only its assigned task. Follow the target repository's own `AGENTS.md` and documentation conventions. The controller's `work-items.md` and `docs/` rules apply only to this repository.
7. Run a separate Codex verification invocation with structured output. It must run every integration test, repair failures, and report actual commands. A failed or missing verification result stops publication.
8. Check the diff, commit without a co-author trailer, push an issue branch using the configured SSH key, and open a PR. Add `done` only after the PR exists. Never merge automatically.
9. On failure, comment with the error and add `swfactory:failed`. Remove that label to retry. Remove the temporary worktree after each attempt.

### Testing

- Unit tests cover queue ordering and filtering, plan validation and formatting, target repository override, scan checkout selection, and the exact repository-view command.
- Manual smoke checks confirm the CLI help, Python syntax, the GitHub CLI repository query, and that the configured SSH key exists. A local Git fixture checks the worktree commands.
- A real issue execution is intentionally not part of local tests because it would publish branches, comments, labels, and a PR to GitHub.

### Limitations and future choices

The local lock prevents concurrent processes on one machine. Coordinating multiple machines requires a stronger remote lease. Codex is asked to run all integration tests, but test coverage depends on the plan and the target repository. The `accept` label is the authorization boundary for code execution in the local worktree, so only trusted maintainers should apply it.

### Sub-issue #5: Issue questions and periodic execution

GitHub issue: [#5](https://github.com/charsyam/swfactory/issues/5) · Parent: [#3](https://github.com/charsyam/swfactory/issues/3) · Implementation PR: [#2](https://github.com/charsyam/swfactory/pull/2)

### What and why

An approved issue can still lack essential requirements. Implementing guessed behavior would produce a PR the owner did not intend. The planner can now return explicit questions, pause the issue, and resume after the configured owner answers in a GitHub issue comment. The existing one-shot command can be scheduled hourly or every two hours through cron.

### Sequence and design

1. Add `questions` to the structured planner response. When it is nonempty, post numbered questions in the source issue with an `@OWNER_GITHUB_HANDLE` mention and a hidden marker identifying the question comment.
2. Replace `swfactory:running` with `swfactory:waiting`. The queue excludes waiting issues, so no implementation begins while the requirement is unresolved.
3. At each one-shot run or watch poll, list waiting issues and their comments. Find the latest swfactory question marker. Resume only if a later comment is authored by the configured owner. Comments by other users do not release the issue.
4. Remove the waiting label and run planning again with recent issue comments as context. If the answer is still incomplete, the planner may ask another focused question.
5. The `OWNER_GITHUB_HANDLE` setting defaults to the repository owner login, and can be explicitly set for an organization repository or a different maintainer.
6. Document cron entries for one-hour and two-hour intervals. Cron invokes the existing one-shot command; a per-repository file lock prevents overlap. Scheduling is not installed automatically because the user has not selected the interval or asked to change their system crontab.

### Tests and limitations

Unit tests check that waiting issues stay out of the normal queue, unrelated comments do not resume an issue, and an owner comment after the latest question does. A live one-shot run on issue #1 recognized the owner's answer and removed `swfactory:waiting`. Cron execution has not been run.

The current completion gate still uses Codex's structured test report. Direct command exit-code verification and GitHub CI checks remain separate future work.

### Sub-issue #6: Rephrase initial issues while preserving the original

GitHub issue: [#6](https://github.com/charsyam/swfactory/issues/6) · Parent: [#3](https://github.com/charsyam/swfactory/issues/3) · Implementation PR: [#2](https://github.com/charsyam/swfactory/pull/2)

### What and why

A user-created issue can be too brief for a coding agent. Every open issue without `rephased` receives an initial specification pass, regardless of approval labels. The rewritten issue explains the understood request, rationale, implementation algorithm and policy, tests, and verified references. The exact original description stays at the bottom below `==== original ====`. A `rephased` label prevents repeated rewrites. An owner-applied `accept` label is the separate authorization for implementation.

### Detailed sequence and policy

1. List all open issues in issue-number order. Exclude those already marked `rephased`, running, waiting, or failed. Recheck labels immediately before starting.
2. Mark the issue running. Read its title, original body, and recent discussion comments, then invoke the local Codex CLI in read-only mode against the configured `PROJECT_PATH` with a structured output schema.
3. Require Codex to ground its specification in repository code and current official documentation or papers. It must list only references it verified, identify assumptions, and ask specific questions when essential facts are missing.
4. Validate that the required fields and at least one reference exist. Write a new Markdown body with sections for what, why, implementation, tests, and references. Preserve the original text after the exact `==== original ====` marker. Use `gh issue edit --body-file` so longer bodies do not exceed the command-line argument limit.
5. Add `rephased` after the body update succeeds. If questions remain, post them with an owner mention and move the issue to `swfactory:waiting`; otherwise remove the running label.
6. The implementation queue skips every issue until `rephased` exists. An issue without an owner-applied `accept` is never implemented, even if rephrasing succeeded.
7. On failure, report the error and add `swfactory:failed`. Removing that label permits retry. If a previous body already contains the original marker, reuse the preserved original instead of nesting another copy.

### Tests

- Verify rephrase queue filtering and ordering.
- Verify accepted issues wait until the rephrase step is complete.
- Verify the original body appears unchanged below the marker.
- Verify the body update and `rephased` label are requested in that order.
- Run the existing unit suite and Python syntax check. A live run on issue #1 rewrote the body, preserved the original below the marker, added `rephased`, and posted owner questions. The issue is waiting for answers and has no `accept` label, so no implementation PR was created.

### Sub-issue #7: Owner-gated implementation and comment filtering

GitHub issue: [#7](https://github.com/charsyam/swfactory/issues/7) · Parent: [#3](https://github.com/charsyam/swfactory/issues/3) · Implementation PR: [#2](https://github.com/charsyam/swfactory/pull/2)

### What and why

GitHub issues and comments can contain instructions from untrusted contributors. The tool may rephrase every new issue in read-only Codex mode, but implementation must start only when the configured owner applied `accept`. Only comments authored by that owner are included as requirement context or accepted as answers to the tool's questions.

### Sequence and policy

1. List issues with `accept`, but do not treat the label's presence alone as authorization.
2. Before marking an issue running for implementation, retrieve its issue events from GitHub. Find the most recent `labeled` or `unlabeled` event for `accept`. Require that the latest event is `labeled` and that its actor is the configured owner. If events are missing or cannot be read, do not implement the issue.
3. Retrieve issue comments through GitHub's paginated API. Pass only owner-authored comments into the rephrase and planning prompts. Keep the issue body as task data and explicitly tell Codex not to follow instructions in it concerning credentials, tools, or workflow.
4. While waiting for answers, recognize the hidden question marker only in comments posted by the authenticated `gh` account. Resume only when a later comment is authored by the configured owner.
5. Recheck the current labels and authorizing event when processing starts, so label removal or a later unauthorized re-add blocks implementation.

### Tests

- Latest `accept` event by another actor is rejected, even when an earlier owner event exists.
- Owner-authored latest `accept` event is accepted.
- Non-owner comments are excluded from Codex context.
- Only an owner answer after the tool's question releases a waiting issue.
- The normal queue requires both `rephased` and `accept`.

### References and limits

- [GitHub issue event types](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types) document `labeled` events, actors, and labels.
- [GitHub issue events API](https://docs.github.com/en/rest/issues/events) returns the event history used for the authorization check.

This filtering does not make issue text itself safe to execute. Codex runs in a worktree with workspace-write access only after owner approval. A future hardening step should pin approved issue content or reject body edits after the owner's approval event.

### Sub-issue #8: Repository-specific GitHub CLI authentication

GitHub issue: [#8](https://github.com/charsyam/swfactory/issues/8) · Parent: [#3](https://github.com/charsyam/swfactory/issues/3) · Implementation PR: [#2](https://github.com/charsyam/swfactory/pull/2)

### What and why

The configured SSH key authenticates Git fetch and push, but GitHub's issue, label, comment, and PR APIs require a token. The machine's global `gh` account is `daemyung-lablup`, which has read-only access to `charsyam/swfactory`; attempting to create a label returned HTTP 404 before issue #1 was changed. Authentication for this tool is now isolated per target repository so it does not change the user's global `gh` account.

### Sequence and policy

1. Derive a stable per-repository `GH_CONFIG_DIR` under `~/.config/swfactory/gh/` using a hash of the configured owner/repository name. Create it with owner-only directory permissions.
2. Set `GH_CONFIG_DIR` in the swfactory process before any GitHub CLI call. Remove inherited `GH_TOKEN` and `GITHUB_TOKEN` values because they override stored `gh` accounts. The parent shell and global `gh` configuration are unaffected.
3. Add `python3 swfactory.py --login`. It invokes the interactive `gh auth login` web/device flow using the isolated config directory. It skips SSH key upload because `GITHUB_SSH_KEY_PATH` already selects the Git transport key.
4. Before normal processing, verify an authenticated account and inspect its effective repository permissions. Stop with a clear error if issue write permission is absent. No issue writes occur on this failure path.
5. Continue to use `GITHUB_SSH_KEY_PATH` for Git fetch and push. This preserves the existing Git transport policy independently of GitHub API authentication.

### Sub-issue #9: Sequential implementation through GitHub sub-issues

GitHub issue: [#9](https://github.com/charsyam/swfactory/issues/9) · Parent: [#3](https://github.com/charsyam/swfactory/issues/3) · Implementation PR: [#2](https://github.com/charsyam/swfactory/pull/2)

### What and why

The parent issue is the owner's approved feature request. A large implementation plan should be split into small, independently understandable tasks that are visible as actual GitHub sub-issues. The previous code wrote only a plan comment on the parent, so task progress was not represented in GitHub's issue structure.

### Detailed sequence and policy

1. Require an owner-applied `accept` label and a completed `rephased` specification before planning implementation. Missing essential information still moves the parent into `swfactory:waiting`.
2. Ask the local Codex CLI for ordered tasks, each containing what, why, a detailed algorithm/implementation policy, and tests. Post the full plan on the parent issue.
3. Before implementing any task, reconcile the plan with existing sub-issues. Each generated child contains a hidden `swfactory-parent:<number> task:<index>` marker, the four required sections, and a `swfactory:subtask` label.
4. Read the parent's linked sub-issues through GitHub's paginated REST endpoint. If a matching child is already linked, reuse it. Otherwise search all repository issues for an unlinked generated child with the same marker and attach it. Only create a new child if neither exists. This limits duplicate issues after a partially completed run.
5. This machine's `gh` version lacks `gh issue create --parent`. Create a child through `gh api POST /repos/{owner}/{repo}/issues`, then attach its numeric issue ID through `POST /repos/{owner}/{repo}/issues/{parent}/sub_issues`. A failed attachment can be recovered on the next run by the marker search.
6. Skip generated `swfactory:subtask` children in the automatic rephrase queue. They have no owner-applied `accept`, so they cannot independently enter implementation.
7. Invoke Codex once per child, in task order, against the same issue worktree. After all task passes, run integration verification. Push the branch and open a PR for the parent. Close each completed sub-issue with a PR reference, then mark the parent `done`. The owner still merges the PR manually.

### Tests

- Verify a newly created child is linked and labeled correctly.
- Verify a linked child is reused on a repeated run without a new write.
- Verify an unlinked generated child is attached to its parent without creating a duplicate.
- Verify generated children are skipped by the rephrase queue.
- Run the existing unit suite and Python syntax check. No live sub-issues were created during this change.

### Sub-issue #10: Link sub-issues in the parent issue body

GitHub issue: [#10](https://github.com/charsyam/swfactory/issues/10) · Parent: [#3](https://github.com/charsyam/swfactory/issues/3) · Implementation PR: [#2](https://github.com/charsyam/swfactory/pull/2)

### What and why

The parent issue must show direct links to every generated sub-issue. GitHub's native sub-issue relationship provides the hierarchy, while links in the parent description keep the ordered work visible alongside the rewritten specification. The original request under `==== original ====` must remain unchanged.

### Detailed sequence and policy

1. Plan and register every sub-issue, recovering existing linked or orphaned generated issues as described under sub-issue #9.
2. Fetch the current parent issue body after registration. Build an ordered Markdown list with each child number, direct GitHub URL, and one-line task description.
3. Place the list in a managed section bounded by `swfactory-subtask-links` HTML comments. Insert that section immediately above `==== original ====`, or append it if the issue has no original marker.
4. On a retry, replace only the managed section. Skip the issue edit if its body already contains the expected links. Reject a partial managed section rather than risking overwriting owner content.
5. Update the parent before starting task implementation. If this update fails, the normal failure path stops implementation; a later retry reuses the already created children.
