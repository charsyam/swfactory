# Work #28: Isolate Codex execution in Docker

Implementation PR: https://github.com/charsyam/swfactory/pull/28
Parent issue: [#15](https://github.com/charsyam/swfactory/issues/15)
Sub-issue: [#26](https://github.com/charsyam/swfactory/issues/26)

## What and why

Every Codex invocation now runs inside a local Docker container. The previous host process inherited controller environment variables and could read same-user GitHub settings or SSH keys. Prompt instructions alone cannot enforce a file access boundary. The owner specified macOS and Linux, a locally authenticated Codex CLI, and target tests that do not require resources outside the worktree.

## Sequence and implementation policy

1. Build `swfactory-codex:0.166.0` from a pinned Node base image with the same pinned Codex CLI version, Python, Git, and ripgrep. `CODEX_CONTAINER_IMAGE` selects a custom image for target test dependencies.
2. Locate the target's Git common directory. Copy only the local file-backed `auth.json` into a private per-repository Codex home on first use; later token refreshes persist there. Do not mount the user's main Codex home, GitHub config, SSH key, or Docker socket.
3. Start Docker with a read-only root, all Linux capabilities dropped, no new privileges, limited PIDs, an explicit host environment, and bind mounts for the worktree, read-only Git metadata, optional result directory, and dedicated Codex home. Read-only calls mount the worktree read-only. Controller GitHub and SSH commands still execute outside the container with their selected credentials.
4. Move rephrase and scan reads to detached snapshots of the fetched default branch. The user's checkout may contain untracked `env` or other private files, which must never be mounted for Codex.
5. Use Codex `read-only` mode for read-only tasks. For implementation and verification, use `danger-full-access` inside the outer Docker boundary because nested `workspace-write` denied writes in the observed Mac Docker runtime. The Docker bind mounts remain the filesystem boundary. Fail without a host Codex fallback when image, Docker, or file-backed login is unavailable.

## Alternative ways

A stripped process environment alone leaves same-user file access. A separate OS account could also create a boundary, but it requires account provisioning and login under that identity on both platforms. Docker was available in the current environment and supplies the same launch model on macOS and Linux. The Codex auth file remains accessible inside the container and should be a dedicated login if that credential also needs separation from generated code.

- Basic: `python3 -m py_compile swfactory.py` — PASS; `git diff --check` — PASS.
- Functional: `python3 -m unittest discover -s tests -q` — PASS, 35 tests. New tests check auth copying, environment allowlist, mount list, read-only and writable launch policies, and snapshot-based rephrasing.
- Integration: `docker build -f docker/Codex.Dockerfile -t swfactory-codex:0.166.0 .` — PASS. A live read-only Codex call produced `OK` through an output file; a live writable Codex call created the requested file in a temporary Git repository — PASS.
