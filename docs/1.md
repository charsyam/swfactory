# Work 1: Approved issue automation

## What and why

`swfactory.py` controls a separate target GitHub repository. It polls that repository's issues bearing `accept`, breaks each issue into small tasks, implements them with the locally installed `codex exec`, tests the result, and opens a PR in the target repository. The owner retains the merge decision. This provides a reviewable boundary between automatic code changes and the main branch.

The user clones the target once and configures both its GitHub SSH URL and local checkout path. Reusing the checkout avoids downloading the full repository for every run. The checkout's `origin` is checked against the GitHub URL to avoid applying an issue to the wrong repository. A separate `WORK_DIR` contains temporary worktrees and run files; it defaults to `/tmp`.

## Sequence and design

1. Read `GITHUB_REPOGITORY`, `GITHUB_SSH_KEY_PATH`, `PROJECT_PATH`, and optional `WORK_DIR` from `env`, or override the target with `--repository` and `--project-path`. Use `/tmp` if `WORK_DIR` is absent. Verify that the existing local Git root and its `origin` match the selected GitHub repository and that `WORK_DIR` is outside the checkout. Use the SSH key only for Git fetch and push. Use the signed-in `gh` CLI for GitHub issue, label, and PR operations.
2. Optionally run `--scan` to inspect the local target checkout and create concrete bug/refactor issues without `accept`. Skip issue titles already present. A maintainer must approve a proposal by applying `accept`.
3. Acquire a local file lock so one process handles the queue at a time. Create required labels if absent. Query open `accept` issues, sort by issue number, and exclude `done`, `swfactory:running`, and `swfactory:failed`.
4. Recheck the selected issue's labels, mark it running, fetch the target's default branch, and create a temporary Git worktree under `WORK_DIR` from the local target repository's fetched commit. The target's main checkout and the `swfactory` source checkout are not modified.
5. Run Codex in read-only mode with a JSON schema. Require a summary, reason, small ordered tasks, detailed algorithms and implementation policies, task tests, and integration tests. Post the plan as a comment on the source issue.
6. Run one Codex invocation per task, in order. Each invocation sees the current worktree and the whole plan but implements only its assigned task. Follow the target repository's own `AGENTS.md` and documentation conventions. The controller's `work-items.md` and `docs/` rules apply only to this repository.
7. Run a separate Codex verification invocation with structured output. It must run every integration test, repair failures, and report actual commands. A failed or missing verification result stops publication.
8. Check the diff, commit without a co-author trailer, push an issue branch using the configured SSH key, and open a PR. Add `done` only after the PR exists. Never merge automatically.
9. On failure, comment with the error and add `swfactory:failed`. Remove that label to retry. Remove the temporary worktree after each attempt.

## Testing

- Unit tests cover queue ordering and filtering, plan validation and formatting, target repository override, scan checkout selection, and the exact repository-view command.
- Manual smoke checks confirm the CLI help, Python syntax, the GitHub CLI repository query, and that the configured SSH key exists. A local Git fixture checks the worktree commands.
- A real issue execution is intentionally not part of local tests because it would publish branches, comments, labels, and a PR to GitHub.

## Limitations and future choices

The local lock prevents concurrent processes on one machine. Coordinating multiple machines requires a stronger remote lease. Codex is asked to run all integration tests, but test coverage depends on the plan and the target repository. The `accept` label is the authorization boundary for code execution in the local worktree, so only trusted maintainers should apply it.
