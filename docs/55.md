# Work #55: Project-scoped SQLite agent dashboard

Implementation PR: https://github.com/charsyam/swfactory/pull/55
Issue: [#54](https://github.com/charsyam/swfactory/issues/54)

## What and why

The controller's console and cron logs did not provide a persistent view of which approved issue was running, which Codex role received a task, or where a handoff failed. The current controller calls Codex sequentially. The dashboard records those actual calls and their transitions; unique invocation IDs allow the same event structure to represent multiple agents later.

## Sequence and implementation policy

1. Resolve `PROJECT_PATH` to its Git common directory and store SQLite at `.git/swfactory/telemetry.sqlite3`. All worktrees belonging to that local clone share the DB. It stays outside tracked source files; `WORK_DIR` remains temporary storage.
2. Initialize a versioned schema with run and event tables. Use WAL, a five-second busy timeout, short connections, and committed event inserts so the controller and local dashboard can use separate connections. A new controller run marks a former unfinished run as interrupted; call start/end events carry a unique invocation ID.
3. Record run start/end, observed queues, issue processing, owner questions, rephrase and scan results, planner output, subtask registration, implementation and verifier calls, test acceptance, PR creation/reuse, merge reconciliation, and failures. Connect each event to repository, run, issue, and task as applicable. Agent events use `controller → role` and `role → controller` directions. Event details contain fixed source categories, counts, file paths, and GitHub references. Do not persist raw issue/comment/prompt text, credentials, or full tool output. A telemetry failure prints a type-only warning and does not block the underlying automation.
4. Add `python3 swfactory.py dashboard [--port N]`. It reads the project's DB without GitHub authentication or a Codex call, binds only to `127.0.0.1`, and exposes a read-only JSON snapshot and local HTML/CSS/JavaScript. The page refreshes every five seconds, displays active calls and recent information flow, links known issue/PR references, and writes untrusted dynamic text with DOM `textContent`. HTTP responses set cache, content sniffing, frame, and content security headers.
5. Document that the history starts with the first instrumented run and is local observation rather than authoritative GitHub state. SQLite WAL is for processes on one host; a shared network-filesystem or distributed controller requires a different store and coordination policy.

## Alternatives

Putting the DB under `WORK_DIR` would separate the history from the target repository and risk losing it during temporary-work cleanup. Putting it in the tracked project tree would pollute Git status or require modifying the target's ignore policy. Using GitHub comments as an event log would add API traffic and expose internal execution metadata. The Git common directory gives the local clone stable, untracked storage.

A hosted dashboard or webhook service would support remote viewing but needs authentication, deployment, and delivery recovery. The local read-only server is the first usable step for this one-host controller.

## Tests and observed results

- Basic: `python3 -m py_compile swfactory.py dashboard.py`, `node --check` on the served JavaScript, and `git diff --check` passed.
- Functional: `python3 -m unittest discover -s tests -q` passed 66 tests (four optional Docker cases skipped). New tests covered concurrent SQLite writes, interrupted runs, Codex prompt/error exclusion, loopback HTTP behavior, safe dynamic rendering, and the project Git metadata DB path.
- Integration: `SWFACTORY_DOCKER_INTEGRATION=1 python3 -m unittest discover -s tests -q` passed all 66 tests, including live Docker and Codex boundary checks.
