# Work 3: Rephrase initial issues while preserving the original

## What and why

A user-created issue can be too brief for a coding agent. Every open issue without `rephased` receives an initial specification pass, regardless of approval labels. The rewritten issue explains the understood request, rationale, implementation algorithm and policy, tests, and verified references. The exact original description stays at the bottom below `==== original ====`. A `rephased` label prevents repeated rewrites. An owner-applied `accept` label is the separate authorization for implementation.

## Detailed sequence and policy

1. List all open issues in issue-number order. Exclude those already marked `rephased`, running, waiting, or failed. Recheck labels immediately before starting.
2. Mark the issue running. Read its title, original body, and recent discussion comments, then invoke the local Codex CLI in read-only mode against the configured `PROJECT_PATH` with a structured output schema.
3. Require Codex to ground its specification in repository code and current official documentation or papers. It must list only references it verified, identify assumptions, and ask specific questions when essential facts are missing.
4. Validate that the required fields and at least one reference exist. Write a new Markdown body with sections for what, why, implementation, tests, and references. Preserve the original text after the exact `==== original ====` marker. Use `gh issue edit --body-file` so longer bodies do not exceed the command-line argument limit.
5. Add `rephased` after the body update succeeds. If questions remain, post them with an owner mention and move the issue to `swfactory:waiting`; otherwise remove the running label.
6. The implementation queue skips every issue until `rephased` exists. An issue without an owner-applied `accept` is never implemented, even if rephrasing succeeded.
7. On failure, report the error and add `swfactory:failed`. Removing that label permits retry. If a previous body already contains the original marker, reuse the preserved original instead of nesting another copy.

## Tests

- Verify rephrase queue filtering and ordering.
- Verify accepted issues wait until the rephrase step is complete.
- Verify the original body appears unchanged below the marker.
- Verify the body update and `rephased` label are requested in that order.
- Run the existing unit suite and Python syntax check. A live run on issue #1 rewrote the body, preserved the original below the marker, added `rephased`, and posted owner questions. The issue is waiting for answers and has no `accept` label, so no implementation PR was created.
