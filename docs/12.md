# Work #12: Use GitHub issue numbers as work numbers

GitHub issue: [#12](https://github.com/charsyam/swfactory/issues/12) · Parent: [#3](https://github.com/charsyam/swfactory/issues/3) · Implementation PR: [#2](https://github.com/charsyam/swfactory/pull/2)

## What and why

The original `work-items.md` used local numbers 1–8 with `docs/1.md`–`docs/8.md`. Those numbers did not identify the actual GitHub work items. GitHub issue #1 is the doctor request, while PR #2 contains the bootstrap implementation, so the local work numbers were misleading.

GitHub issues and pull requests share a repository number sequence. Their identifiers cannot be forced to match. The canonical work number is therefore the GitHub issue number; the implementation PR is a separate cross-reference.

## Detailed sequence and policy

1. Create bootstrap tracking issue #3 with a detailed specification, without `accept`, because this is a record of already implemented work rather than a new authorization to implement it.
2. Register the eight existing implementation units as native GitHub sub-issues #4–#11. Add a ninth sub-issue #12 for this numbering correction. Each child points to PR #2 and carries the `swfactory:subtask` label.
3. Move the eight existing design records to `docs/4.md`–`docs/11.md`, and write this record as `docs/12.md`. Retain their implementation and test histories while changing the work number to the corresponding issue number.
4. Replace the local work item table with rows keyed by issue #4–#12 and link the implementation PR separately. Add ordered direct links to the parent issue body.
5. Tell each future Codex implementation pass to use the sub-issue number for work records. If the target repository's `AGENTS.md` requires `work-items.md` and `docs/{work number}.md`, verify that every sub-issue has its matching document and table row before publishing a PR.

## Tests and observed results

- The issue registry returned #4–#12 for the nine work items; all were attached to parent #3.
- The unit suite passed 23 tests after the migration; the Python syntax and diff checks also passed.
- A unit test checks issue-numbered record validation, including failure when a document or row is missing.

## Alternative

A local counter could remain in the documents with an explicit issue mapping column. It would preserve old filenames but require two identifiers for each task and allow future numbering drift. Using the issue number directly keeps one work identifier.
