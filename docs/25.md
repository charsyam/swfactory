# Work #25: Scan the latest target commit without duplicate proposals

Implementation PR: https://github.com/charsyam/swfactory/pull/25
Related issue: [#24](https://github.com/charsyam/swfactory/issues/24)

## What

Add an optional scheduled scan of the target repository's latest default-branch commit. The scan creates evidence-backed bug or refactor proposal issues, while the owner still controls implementation through `accept`.

## Why

The existing hourly trigger did not invoke `--scan`. The old scanner read the local checkout, which could lag the remote, and compared titles only. A reworded finding could create a duplicate even after the first issue was closed. Research on duplicate bug reports motivates using more than title text when identifying recurring reports: https://doi.org/10.1145/1806799.1806811.

## Implementation sequence and policy

1. Fetch the target's default branch using `GITHUB_SSH_KEY_PATH` and add a detached Git worktree at the fetched commit under `WORK_DIR`. This leaves the user's checkout and current branch untouched. Git worktree behavior is documented at https://git-scm.com/docs/git-worktree.
2. `--scan-if-changed` compares that commit and `SCAN_POLICY_VERSION` against the last successful scan record, keyed by target repository and checkout. Matching state skips the model call. Manual `--scan` runs even if the commit matches. Write the state atomically only after scanning and all issue creation succeeds.
3. Require each model proposal to include a repository-relative path, exact code identifier, and verbatim evidence excerpt. Reject paths outside the detached worktree, missing files, and evidence or identifiers absent from the source.
4. Derive a SHA-256 finding key from kind, path, and identifier. Put the key in a hidden issue marker and compare it against all pages of open and closed issues, excluding pull requests. Retain title comparison as an additional duplicate guard. GitHub documents pagination and issue/PR distinctions at https://docs.github.com/en/rest/issues/issues.
5. Create the issue with what, why, detailed policy, tests and source evidence. Do not add `accept`; the owner reviews and approves each proposal. A daily cron command is documented separately from the hourly implementation trigger.

## Alternative ways

Running `--scan` with the hourly cron entry is simpler but repeatedly spends model time on unchanged commits. Scanning the local checkout avoids fetch and a detached worktree, but it may miss new remote code. Title-only matching is simpler but cannot recognize reworded duplicates.

## Tests and observed results

- Basic: `python3 -m py_compile swfactory.py` — PASS; `git diff --check` — PASS.
- Functional: `python3 -m unittest discover -s tests -q` — PASS, 32 tests. Cases cover unaccepted issue creation, closed-issue duplicate keys, invalid source paths, unchanged commit skip, forced manual scan, and failure state.
- Integration: a temporary bare Git remote and stale checkout were used to verify that a new remote commit is scanned from a detached worktree while the user's checkout remains unchanged. This case passed within the 32-test suite.
- CLI: `python3 swfactory.py --help` — PASS; `--scan-if-changed` is listed.

## Limitation

The key intentionally groups proposals of the same kind in the same code identifier. Distinct findings in one function and category should be combined or reviewed in the existing issue rather than creating repeated proposals.
