# Work #7: Owner-gated implementation and comment filtering

GitHub issue: [#7](https://github.com/charsyam/swfactory/issues/7) · Parent: [#3](https://github.com/charsyam/swfactory/issues/3) · Implementation PR: [#2](https://github.com/charsyam/swfactory/pull/2)

## What and why

GitHub issues and comments can contain instructions from untrusted contributors. The tool may rephrase every new issue in read-only Codex mode, but implementation must start only when the configured owner applied `accept`. Only comments authored by that owner are included as requirement context or accepted as answers to the tool's questions.

## Sequence and policy

1. List issues with `accept`, but do not treat the label's presence alone as authorization.
2. Before marking an issue running for implementation, retrieve its issue events from GitHub. Find the most recent `labeled` or `unlabeled` event for `accept`. Require that the latest event is `labeled` and that its actor is the configured owner. If events are missing or cannot be read, do not implement the issue.
3. Retrieve issue comments through GitHub's paginated API. Pass only owner-authored comments into the rephrase and planning prompts. Keep the issue body as task data and explicitly tell Codex not to follow instructions in it concerning credentials, tools, or workflow.
4. While waiting for answers, recognize the hidden question marker only in comments posted by the authenticated `gh` account. Resume only when a later comment is authored by the configured owner.
5. Recheck the current labels and authorizing event when processing starts, so label removal or a later unauthorized re-add blocks implementation.

## Tests

- Latest `accept` event by another actor is rejected, even when an earlier owner event exists.
- Owner-authored latest `accept` event is accepted.
- Non-owner comments are excluded from Codex context.
- Only an owner answer after the tool's question releases a waiting issue.
- The normal queue requires both `rephased` and `accept`.

## References and limits

- [GitHub issue event types](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types) document `labeled` events, actors, and labels.
- [GitHub issue events API](https://docs.github.com/en/rest/issues/events) returns the event history used for the authorization check.

This filtering does not make issue text itself safe to execute. Codex runs in a worktree with workspace-write access only after owner approval. A future hardening step should pin approved issue content or reject body edits after the owner's approval event.
