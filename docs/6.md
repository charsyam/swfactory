# Work 6: Sequential implementation through GitHub sub-issues

## What and why

The parent issue is the owner's approved feature request. A large implementation plan should be split into small, independently understandable tasks that are visible as actual GitHub sub-issues. The previous code wrote only a plan comment on the parent, so task progress was not represented in GitHub's issue structure.

## Detailed sequence and policy

1. Require an owner-applied `accept` label and a completed `rephased` specification before planning implementation. Missing essential information still moves the parent into `swfactory:waiting`.
2. Ask the local Codex CLI for ordered tasks, each containing what, why, a detailed algorithm/implementation policy, and tests. Post the full plan on the parent issue.
3. Before implementing any task, reconcile the plan with existing sub-issues. Each generated child contains a hidden `swfactory-parent:<number> task:<index>` marker, the four required sections, and a `swfactory:subtask` label.
4. Read the parent's linked sub-issues through GitHub's paginated REST endpoint. If a matching child is already linked, reuse it. Otherwise search all repository issues for an unlinked generated child with the same marker and attach it. Only create a new child if neither exists. This limits duplicate issues after a partially completed run.
5. This machine's `gh` version lacks `gh issue create --parent`. Create a child through `gh api POST /repos/{owner}/{repo}/issues`, then attach its numeric issue ID through `POST /repos/{owner}/{repo}/issues/{parent}/sub_issues`. A failed attachment can be recovered on the next run by the marker search.
6. Skip generated `swfactory:subtask` children in the automatic rephrase queue. They have no owner-applied `accept`, so they cannot independently enter implementation.
7. Invoke Codex once per child, in task order, against the same issue worktree. After all task passes, run integration verification. Push the branch and open a PR for the parent. Close each completed sub-issue with a PR reference, then mark the parent `done`. The owner still merges the PR manually.

## Tests

- Verify child formatting and the marker.
- Verify a newly created child is linked and labeled correctly.
- Verify a linked child is reused on a repeated run without a new write.
- Verify an unlinked generated child is attached to its parent without creating a duplicate.
- Verify generated children are skipped by the rephrase queue.
- Run the existing unit suite and Python syntax check. No live sub-issues were created during this change.
