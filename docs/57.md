# Work #57: Issue workflow and agent handoffs in the dashboard

Implementation PR: https://github.com/charsyam/swfactory/pull/57
Issue: [#56](https://github.com/charsyam/swfactory/issues/56)
Depends on [work #55](https://github.com/charsyam/swfactory/pull/55).

## What and why

The first dashboard showed recent events in one chronological list. It did not let an owner follow one issue from its specification through planning, subtasks, code, tests, and PRs, or directly relate a Codex call to its output. Its 200-event overview limit also hid earlier steps of long jobs. This work adds an issue-centered view derived from the project-local event history. The repository had no local telemetry when the dashboard was first opened, so this work also adds current GitHub metadata to make existing work visible.

## Sequence and implementation policy

1. Keep the existing SQLite schema and project Git common-directory location. Query issue numbers and their last activity for the overview. Read one selected issue's full event stream for stage and call summaries, while returning its visible timeline in 100-event cursor pages. This avoids making the overview's 200-event cap the limit of an issue investigation.
2. Map observed events to specification, plan, subtasks, implementation, optional experiments, tests, PR, and merge stages. Display a stage as pending until an event establishes it; do not infer completion from GitHub state that has not been recorded. Track owner questions, failures, retries, ready-for-review, and merged closure separately.
3. Give every Codex call a stable invocation ID, a source-category list, safe GitHub input references, and an elapsed time measured with a monotonic clock. Attach the later plan, continuity result, worktree-change summary, or test result to the same ID. The handoff pair is controller-to-role at start and role-to-controller at completion. The controller remains sequential today; the data model does not claim concurrent agents exist.
4. Record a SHA-256 of the structured plan rather than its raw text. Record task count, child issue numbers, changed-entry count, test case count and categories, and PR URLs as output references. Classify issue failures by fixed reason codes and link to the owner-visible GitHub issue for the detailed diagnostic. Keep prompts, comments, credentials, and complete command output out of SQLite.
5. Extend the read-only loopback HTTP API with `/api/issues` and `/api/issues/<number>` and a `/issue/<number>` view. Return stage summaries, call handoffs, result records, optional performance measurements, and a paged timeline. All dynamic text uses DOM `textContent`; GitHub links are constructed or checked before being attached. The performance section appears only when `performance_measurement` events exist. Producing those events is part of the separate optimization feature.
6. Query GitHub issues and PRs using the repository-specific `gh` profile, with read-only list commands and a one-minute in-memory cache. Connect PRs using GitHub's closing-issue references. Do not request issue bodies or comments. Preserve the last successful snapshot with a visible stale indication if GitHub fails. An issue with no local events still opens and shows GitHub state; unknown agent stages remain explicitly unknown.
7. Reorganize the owner view around decisions: answer questions, recover failures, review and merge PRs, and approve specifications. Put running/accepted work in a separate automation lane. Each issue row explains the next action and shows child completion and linked PR progress. Use GitHub's native sub-issue API to recover relationships even when child titles do not contain a parent number; query likely parent issues with bounded concurrency and a one-minute cache. Keep PRs lacking a closing-issue reference in a separate linkage check. The issue view shows parent/child/PR delivery paths first, then recorded test evidence and agent handoffs; hide empty trace sections and explicitly say when verification is not locally recorded. Keep all browser text as `textContent` and construct PR URLs from the selected repository and numeric PR ID.

## Alternatives

Rendering only the latest flat events is simpler but loses the causal path for long work. Storing raw prompts and tool output would permit richer replay but would also persist untrusted text and possibly credentials. A distributed tracing service could support multiple hosts, but the current controller and SQLite store are local; run and invocation IDs provide the correlation needed for this stage. Dapper's tracing model is a conceptual reference for correlating work across components, not a claim that this implementation speaks a tracing protocol. Synthetic historical agent events inferred from GitHub labels would misstate which agents ran, so the GitHub state is shown separately. Querying GitHub on every five-second page refresh would add avoidable API use, so the snapshot is cached. A flat issue/PR inventory answered how many objects exist but not what the owner should do; the decision hierarchy addresses that without changing GitHub workflow state.

## Tests and observed results

- Basic: Python compilation, `node --check` for both served scripts, and `git diff --check` passed.
- Functional: `python3 -m unittest discover -s tests -q` passed 82 tests (four optional Docker cases skipped). New tests cover more than 200 events, issue grouping and status, stage and call/result linkage, elapsed time, performance data, failure/retry state, API paging, validation, safe rendering, native sub-issue and PR relationships, body exclusion, cache reuse, stale data after a query error, and decision-group precedence.
- Integration: `SWFACTORY_DOCKER_INTEGRATION=1 python3 -m unittest discover -s tests -q` passed all 80 tests, including live Docker and Codex boundary checks.
- Live GitHub read: the isolated project profile returned 43 issues and 14 PRs; native relationships linked #3 to nine subtasks and #32/#33 to eight each. The board placed #3 under owner answers, #32/#33 under failure recovery, #56 under PR review, and #53 under automation queue. The server returned HTTP 200 for the board, issue view, and scripts without a controller run.
